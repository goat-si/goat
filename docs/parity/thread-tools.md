# Agent-facing thread tools: v1 parity

Scope: local and routed agent-facing thread send, wait, watch, unwatch, watch_list and report_result, with status/read only where they affect those tools. This is a source-level behavioral inventory, not a runtime certification; traces below are proposed semantic projections, not verbatim v1 events.

Pinned v1: `916b5ccc1b2b6d4ecd991ab1573172bab8fb1cc4` (`goat-si/goat` origin/dev, 2026-11-28), read from `/tmp/goat-v1-916b5cc`.

## Rules

1. **R1 — caller identity.** OBSERVED: A thread caller is supplied in invocation scope, including server-issued run identity; a remote sender label is not authority. Send and wait admit thread or outside client callers, whereas watch, unwatch, watch_list and report_result require a calling GOAT thread. Refs: `apps/server/src/mcp/McpInvocationContext.ts:35-46`, `apps/server/src/mcp/McpInvocationContext.ts:175-188`, `packages/contracts/src/orchestratorMcp.ts:768-780`, `packages/contracts/src/agentSurface/entries/thread.ts:275-278`, `packages/contracts/src/agentSurface/entries/thread.ts:317-320`, `packages/contracts/src/agentSurface/entries/thread.ts:536-541`, `packages/contracts/src/agentSurface/entries/thread.ts:572-577`, `packages/contracts/src/agentSurface/entries/thread.ts:595-598`, `packages/contracts/src/agentSurface/entries/thread.ts:681-690`, `packages/contracts/src/agentSurface/entries/thread.ts:723-727`.

2. **R2 — scope and permissions.** OBSERVED: Send is not restricted to direct children: it resolves the specified thread, checks a live caller for cross-thread sends, enforces runtime and interaction ceilings, and checks `threads.launch` and target permission for another thread. Wait resolves the target through scoped thread loading; remote calls additionally use host access checks. Refs: `apps/server/src/mcp/OrchestratorMcpService.ts:3423-3457`, `apps/server/src/mcp/OrchestratorMcpService.ts:3508-3524`, `packages/contracts/src/agentSurface/entries/thread.ts:243-245`, `apps/server/src/mcp/OrchestratorMcpService.test.ts:1254-1303`.

3. **R3 — send contract.** OBSERVED: `thread.send` accepts `threadId`, `message` (up to 120000 characters), optional `host`, `mode` (`auto`, `queue`, `steer`, `restart`), `capabilities` and `clientRequestId`; forwarding-only fields are not caller authority. Delivery reports `started`, `queued`, `steered` or `restarted`, a message and run ID, status and sometimes task ID; `relayed` reports only a handoff via the launching host, not target acceptance. Refs: `packages/contracts/src/orchestratorMcp.ts:768-810`, `packages/contracts/src/agentSurface/entries/thread.ts:243-255`, `apps/server/src/mcp/OrchestratorMcpService.ts:3498-3506`.

4. **R4 — effective mode.** OBSERVED: From a different GOAT thread, every mode except `restart` becomes `steer_when_ready`; even an explicit `queue` may join the active turn. Self-send and outside callers retain explicit queue and steer, while default `auto` is `steer_when_ready`. Refs: `apps/server/src/orchestration-v2/ThreadSendMode.ts:4-19`, `apps/server/src/orchestration-v2/AgentThreadSteering.integration.test.ts:316-334`.

5. **R5 — dispatch.** OBSERVED: The MCP handler calls host routing, then local send constructs a stable message and command ID and calls thread management with `createdBy: agent`, `creationSource: mcp`; management dispatches `message.dispatch` with the selected mode. A send into an idle target can start a run; its response does not establish completion. Refs: `apps/server/src/mcp/toolkits/orchestrator/handlers.ts:260-267`, `apps/server/src/mcp/OrchestratorMcpService.ts:3430-3440`, `apps/server/src/mcp/OrchestratorMcpService.ts:3459-3506`, `apps/server/src/orchestration-v2/ThreadManagementService.ts:1029-1070`, `apps/server/src/orchestration-v2/AgentThreadSteering.integration.test.ts:506-516`.

6. **R6 — starting and races.** OBSERVED: A cross-thread send waits for a starting turn to become steerable; after its deadline it is durably queued and can be promoted into that turn. A refusal because the turn stopped or ended is reconsidered once against the observed turn; a user stop can prevent delivery rather than silently restarting. Refs: `apps/server/src/orchestration-v2/ThreadManagementService.ts:1222-1255`, `apps/server/src/orchestration-v2/AgentThreadSteering.integration.test.ts:373-389`, `apps/server/src/orchestration-v2/AgentThreadSteering.integration.test.ts:629-650`, `apps/server/src/orchestration-v2/AgentThreadSteering.integration.test.ts:692-740`, `packages/contracts/src/agentSurface/entries/thread.ts:243-245`.

7. **R7 — unsupported or explicit steer.** OBSERVED: A provider that steers through interrupt/restart may restart; a provider without either steering mechanism, a finishing turn, or `/compact`, `/logout`, `/goal` takes a next turn. For a fresh self/outside explicit steer or restart with no existing receipt, no steerable run produces a `ThreadManagementNoSteerableRunError`; do not conflate these cases with provider refusal of an actual steer. Refs: `packages/contracts/src/agentSurface/entries/thread.ts:243-245`, `apps/server/src/orchestration-v2/ThreadManagementService.ts:1417-1449`, `apps/server/src/orchestration-v2/AgentThreadSteering.integration.test.ts:549-593`, `apps/server/src/orchestration-v2/AgentThreadSteering.integration.test.ts:610-620`.

8. **R8 — special send restrictions.** OBSERVED: Restart may be refused when stop/restart conditions or special commands disallow it; computer-use origin gating can put unattended cross-thread steering into a next turn. Fresh agent sends to a child are rejected when its latest app-owned task is a finished review and no matching task is pending, running or waiting; existing message-ID replay precedes this check. Otherwise, another eligible follow-up to a completed delegated child can create a fresh task, retaining the original task result. Refs: `packages/contracts/src/agentSurface/entries/thread.ts:243-245`, `apps/server/src/orchestration-v2/ThreadManagementService.ts:997-1027`, `apps/server/src/orchestration-v2/ThreadManagementService.ts:1341-1389`, `apps/server/src/orchestration-v2/ThreadManagementService.ts:1417-1418`.

9. **R9 — send retry.** OBSERVED: Send has domain idempotency through its orchestration receipt, with `clientRequestId` forwarded locally; remote routing has a session boundary and `keyIgnoredWith: [host]`, so do not promise durable cross-session remote deduplication. The dispatch command and message IDs are derived from the request key; a replay can return the original delivery. Refs: `packages/contracts/src/agentSurface/entries/thread.ts:275-283`, `apps/server/src/mcp/OrchestratorMcpService.ts:3435-3440`, `apps/server/src/mcp/OrchestratorMcpService.ts:3459-3476`, `apps/server/src/orchestration-v2/SteeringReceiptReplay.integration.test.ts:45-87`, `packages/contracts/src/agentSurface/idempotencyReasons.ts:7-12`.

10. **R10 — generic admission.** OBSERVED: For registry-keyed writes, ToolAdmission reserves by environment, principal, path and client request ID, with digest and receipt; replay is conditional on the caller retaining the original grant. This generic mechanism must not be assumed to replace send's domain receipt. Refs: `apps/server/src/mcp/ToolAdmission.ts:200-228`, `apps/server/src/mcp/ToolAdmission.ts:417-436`, `apps/server/src/mcp/ToolAdmission.ts:546-620`, `packages/contracts/src/agentSurface/entries/thread.ts:281-283`.

11. **R11 — wait selection and timeout.** OBSERVED: `thread.wait` takes `threadId`, optional `host`, `runId`, finite `timeoutMs`, up to 50 `ignoreRequestIds`, and `untilDelegatedWorkSettled`. Without runId it selects the latest at call time; idle returns immediately, an unknown explicit run is an error, and the service clamps timeout to 1 ms–1 hour with a 10-minute default. Refs: `packages/contracts/src/orchestratorMcp.ts:814-822`, `apps/server/src/mcp/OrchestratorMcpService.ts:170-171`, `apps/server/src/mcp/OrchestratorMcpService.ts:3508-3524`, `apps/server/src/orchestration-v2/ThreadManagementService.ts:1460-1476`.

12. **R12 — wait release.** OBSERVED: A terminal run or a pending user-input question releases wait; ignored question IDs do not. An approval alone is not a listed release condition: wait's predicate specifically finds `user_input_request` and terminal status, so approval can leave the call waiting until another release or timeout. Refs: `apps/server/src/orchestration-v2/ThreadManagementService.ts:1500-1555`, `apps/server/src/orchestration-v2/ThreadManagementService.test.ts:787-872`, `packages/contracts/src/agentSurface/entries/thread.ts:295-307`.

13. **R13 — wait continuation and result.** OBSERVED: Wait follows a restart continuation instead of treating its cut predecessor as the final answer; optional delegated-work settlement can wait through descendants and later wake runs, including later questions. A timeout leaves work running; terminal local results are added by the MCP handler, and waiting does not acknowledge a child result. Refs: `apps/server/src/orchestration-v2/ThreadManagementService.ts:1500-1555`, `apps/server/src/orchestration-v2/ThreadManagementService.test.ts:206-255`, `apps/server/src/orchestration-v2/ThreadManagementService.delegatedWork.test.ts:219-279`, `apps/server/src/mcp/toolkits/orchestrator/handlers.ts:269-279`, `packages/contracts/src/agentSurface/entries/thread.ts:295-309`.

14. **R14 — watch registration.** OBSERVED: `thread.watch({threadId, host?, checkpointReplication?})` is keyed by caller, host and target and upserts; it follows the active run or an unreported latest run. A thread launch normally watches automatically; subsequent sends by that caller re-arm the relevant run. Refs: `packages/contracts/src/orchestratorMcp.ts:932-942`, `packages/contracts/src/agentSurface/entries/thread.ts:524-541`, `apps/server/src/mcp/LaunchWatchService.test.ts:54-125`.

15. **R15 — watch wake.** OBSERVED: A watch delivers a message to the calling thread on followed run end or a user-input question, and reports sustained host outage once per outage; a completion report includes answer and branch. It follows the target's own subsequent wake runs, whereas a run started by another sender is reported to that sender's watch; the public watch guide does not promise approval notifications; the v1 test nevertheless observes an approval notification on a later follower tick. Refs: `packages/contracts/src/agentSurface/entries/thread.ts:529-535`, `apps/server/src/mcp/LaunchWatchService.test.ts:54-93`, `apps/server/src/mcp/LaunchWatchService.test.ts:179-208`, `apps/server/src/mcp/LaunchWatchService.test.ts:730-760`.

16. **R16 — watch persistence and expiry.** OBSERVED: Pending watches resume after host restart; dormant watches expire after a week without changes, and the watch is dropped if the launcher is archived while waiting. Unreadable watch state is not silently overwritten when it cannot be read. Refs: `apps/server/src/mcp/LaunchWatchService.test.ts:155-178`, `apps/server/src/mcp/LaunchWatchService.ts:110-116`, `apps/server/src/mcp/launchWatch.ts:624-646`, `apps/server/src/mcp/LaunchWatchService.test.ts:1288-1312`, `apps/server/src/mcp/LaunchWatchService.test.ts:1589-1608`.

17. **R17 — unwatch and list.** OBSERVED: `thread.unwatch` removes only the caller's watch, returns `removed:false` if absent, and does not stop the target; local questions may still escalate independently. For a remote launched target, prolonged unreachability can also stop report tracking (`reportsStopped`); `watch_list` is a read of the caller's watches, pending/reported runs and reachability. Refs: `packages/contracts/src/agentSurface/entries/thread.ts:549-560`, `packages/contracts/src/agentSurface/entries/thread.ts:585-598`, `packages/contracts/src/orchestratorMcp.ts:944-955`, `apps/server/src/mcp/LaunchWatchService.test.ts:1235-1255`.

18. **R18 — own result only.** OBSERVED: `thread.report_result` acts on the authenticated calling thread, not a target argument, and records or replaces a result without ending the run. It reports to durable per-thread/run storage for read/wait and completion delivery; status supplies `runId` and `activeAttemptId` to capture at work start. Refs: `apps/server/src/mcp/toolkits/thread/handlers.ts:84-102`, `apps/server/src/mcp/toolkits/thread/tools.ts:247-258`, `packages/contracts/src/agentSurface/entries/thread.ts:681-690`, `apps/server/src/threadResults/ThreadResultService.ts:340-356`.

19. **R19 — result payload and replacement.** OBSERVED: Outcome is succeeded/failed/blocked/cancelled; optional summary is at most 4000 characters, PRs at most 20, commits at most 100 matching hexadecimal SHA syntax, branch at most 512 characters, plus tests and relevance. Upsert replaces report fields per run, but previously retained attachment references are preserved and deduplicated; report PRs are merged ahead of linked PRs, with duplicate URLs omitted. Refs: `packages/contracts/src/threadResult.ts:30-63`, `packages/contracts/src/threadResultEvidence.ts:1-34`, `apps/server/src/threadResults/ThreadResultService.ts:90-139`, `apps/server/src/threadResults/ThreadResultService.ts:321-345`, `apps/server/src/threadResults/ThreadResultService.test.ts:100-147`.

20. **R20 — provenance and attachments.** OBSERVED: Without explicit runId the service selects latest active, then latest; an explicit run must belong to this thread, and relevance requires runId. At most eight attachment refs per report must point to this thread's message attachments; reports with attachments require explicit `runId` and `expectedAttemptId` matching that run's current `activeAttemptId`. The validation does not establish that the attachment originated in that run; up to 128 distinct refs remain on a run. Refs: `apps/server/src/threadResults/ThreadResultService.ts:265-281`, `apps/server/src/threadResults/ThreadResultService.ts:292-308`, `apps/server/src/threadResults/ThreadResultService.ts:321-337`, `packages/contracts/src/threadResult.ts:43-52`, `apps/server/src/threadResults/ThreadResultService.test.ts:317-349`.

21. **R21 — reporting refusal.** OBSERVED: A bot with outstanding delegated results gets `Delegated results are outstanding. Wait for their notifications or read the results with task.status, then report what each task returned.`; a bot’s success report with unaccepted required deliverables is refused too. Missing run says `The thread has no run to report on.`; wrong run says `The report does not identify a run belonging to this thread.` These non-storage failures map to MCP `invalid_request`; storage maps to unavailable. Refs: `apps/server/src/threadResults/ThreadResultService.ts:35-69`, `apps/server/src/threadResults/ThreadResultService.ts:282-290`, `apps/server/src/threadResults/ThreadResultService.ts:310-320`, `apps/server/src/mcp/toolkits/thread/handlers.ts:92-100`, `apps/server/src/threadResults/ThreadResultService.test.ts:177-194`, `apps/server/src/threadResults/ThreadResultService.test.ts:283-290`.

22. **R22 — surface envelope and failures.** OBSERVED: The generic surface wraps success as `status:ok`, failures as `status:error` with classified `code`, domain `reason`, message and `retryable`, and human handoff as `needs_human`. `thread_not_found`/`run_not_found` classify as `not_found`, `thread_not_sendable` as `conflict`, mode escalation as `permission_denied`, `host_unavailable` as `unavailable` with potentially uncertain remote outcome, and `orchestration_error` as `internal`. Refs: `packages/contracts/src/agentSurface/envelope.ts:23-30`, `packages/contracts/src/agentSurface/envelope.ts:72-89`, `packages/contracts/src/agentSurface/envelope.ts:109-131`, `packages/contracts/src/agentSurface/envelope.ts:150-156`.

23. **R23 — status and read distinction.** OBSERVED: Status is a nonblocking snapshot including run phase and caller's watch; waiting does not acknowledge a delegated result, but reading summary or tail of a finished direct task child can acknowledge its automatic completion delivery. Refs: `packages/contracts/src/agentSurface/entries/thread.ts:328-345`, `packages/contracts/src/agentSurface/entries/thread.ts:290-299`, `apps/server/src/mcp/OrchestratorMcpService.ts:3398-3420`.

## Parity scenarios

INFERRED: These are proposed trace projections, not executed results. Events are scoped slices; `input` and `run` are aliases, text is optional, and tool results carry a call alias. Wake transitions require evidence: v1 queued requires a queued wake run, started a running wake run, steered proven delivery, cancelled a cancelled wake run. GOAT 2 queued wake remains pending; requested mode alone is not evidence. Watch wake is deferred. A transcript named below is a candidate fixture, not proof it already drives the MCP path.

### cross_thread_queue_steers

- Setup: caller A and target B, B running and steerable; both admitted.
- Steps: A calls `thread.send` with `threadId:B`, `mode:queue`, message and stable key; retry with the same key.
- Expected: `run.started {thread:B,run:r1,inputs:[initial]}` → `input.accepted {thread:B,input:i1,from:agent,mode:steer,text:"message"}` → `tool.result {thread:A,call:c1,path:thread.send,status:ok}` → `tool.result {thread:A,call:c2,path:thread.send,status:ok}`; independently observe one `steer.applied {thread:B,run:r1,input:i1}`. Its ordering relative to the replies is not established.
- Driver: MCP handler plus `AgentThreadSteering.integration.test.ts` harness; candidate transcript `fixtures/message_steering/codex_transcript.ndjson`. Refs: `apps/server/src/orchestration-v2/AgentThreadSteering.integration.test.ts:316-362`, `apps/server/src/mcp/toolkits/orchestrator/handlers.ts:260-267`.

### starting_turn_queue_promotes

- Setup: A sends to B while B is starting and remains unsteerable past the send deadline.
- Steps: call `thread.send`; then make B steerable and finish the run.
- Expected: `run.started {thread:B,run:r1,inputs:[initial]}` → `input.accepted {thread:B,input:i1,from:agent,mode:queue,text:"message"}` → `queue.changed {thread:B,input:i1,op:enqueued}` → `tool.result {thread:A,call:c1,path:thread.send,status:ok}` → `queue.changed {thread:B,input:i1,op:promoted}` → `steer.applied {thread:B,run:r1,input:i1}` → `run.finished {thread:B,run:r1,status:done}`.
- Driver: thread-management steering harness with controlled readiness; candidate `fixtures/message_steering/codex_transcript.ndjson` or `fixtures/queued_turn/codex_transcript.ndjson`. Refs: `apps/server/src/orchestration-v2/ThreadManagementService.ts:1222-1226`, `apps/server/src/orchestration-v2/AgentThreadSteering.integration.test.ts:716-740`.

### question_wait_and_approval
