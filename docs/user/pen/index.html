Pen

Pen joins your machines into a private mesh. Each machine gets a name, and any member can reach a local port on any other member through an end-to-end encrypted pipe, even when neither machine accepts incoming connections. GOAT uses this to reach a machine over SSH as pen-<name>, so a laptop, a home server and a cloud box can work together without a VPN, port forwarding or a public address.

Pen runs as a small command-line program and background service on each machine. Traffic passes through relays, which forward it without being able to read it.

Before you start

  • Pen runs on macOS, Linux and Windows 10 or 11 (x86-64 and ARM).
  • Every member trusts every other member fully: a member can open any port that listens on 127.0.0.1 of another member, as if it were local. Add only machines you control, and remove a machine you no longer trust (see Remove a machine).
  • Installing downloads Pen from the relay that serves it and checks the download against the checksums the same relay publishes. That proves the file arrived intact; it does not protect you from the relay’s operator.

Install Pen

curl -fsSL https://pen-relay.pos090001.workers.dev/install.sh | sh

This puts pen in ~/.local/bin and prints what to run next. It does not start or join a mesh. When ~/.local/bin is not on your PATH, it adds one marked line to your shell’s startup files (.zshenv in $ZDOTDIR or your home for zsh, ~/.bashrc and ~/.bash_profile or ~/.profile for bash, otherwise ~/.profile), so new terminals find pen; for fish it prints the fish_add_path line to run instead. curl ... | PEN_NO_MODIFY_PATH=1 sh leaves your files alone. To install and connect in one step, add one of these after sh -s --:

Option What it does
--login Sign in with Google and join your account’s mesh, or start one.
--join <token> Join the mesh an invite token comes from.
--up Start a new mesh with this machine as its first member.
--name <name> Name this machine (with any of the three above).

For example: curl -fsSL https://pen-relay.pos090001.workers.dev/install.sh | sh -s -- --login.

On Windows, run this in PowerShell:

& ([scriptblock]::Create((irm https://pen-relay.pos090001.workers.dev/install.ps1)))

This puts pen.exe in %LOCALAPPDATA%\Programs\pen and adds that folder to your PATH for new terminals. The same options go after the last parenthesis, for example ... install.ps1))) --login. Set $env:PEN_NO_MODIFY_PATH = '1' first to leave your PATH alone.

Sign in with Google

pen login (or install.sh --login) prints a short code and an address. Open the address in any browser, type the code, and sign in with Google. The page shows the machine’s name and fingerprint; check them against the terminal before you add it.

The first machine you sign in starts a mesh for your Google account. Each later machine you sign in with the same account joins that mesh: Pen shows the account’s mesh and members and asks you to confirm (--yes skips the question). A member must be online to admit the new machine; if none is, pen login says so and retries every 5 seconds until the sign-in expires after 10 minutes. With the mesh locked, it waits up to 30 minutes for approval.

pen logout removes this machine from your account’s machine list. It stays in the mesh. pen account unbind, on any member, turns Google sign-in off for the mesh; invites keep working.

The account’s machine list is kept by the sign-in service, and it only decides which mesh a new machine is offered. Anyone who signs in to your Google account, even once, can add a machine to that list or remove the others from it, so new machines might be offered the wrong mesh; machines already in your mesh and invites are not affected. If that may have happened, turn on pen lock on so new machines need your approval, change your Google password, clear the list from the reset link on the sign-in page, and run pen login on one of your machines to register your mesh again.

Require approval for new machines

pen lock on makes every newly signed-in machine wait for approval. Its pen login names the member that holds the request and prints the new machine’s fingerprint. On that member, run pen approve to list requests, and pen approve '<fingerprint>' with the full fingerprint you read on the new machine to admit it. pen deny <id> refuses a request for 24 hours. pen lock off returns to automatic admission.

Lock the mesh if someone else might be able to sign in to your Google account, or as soon as a signed-in machine is lost.

Join with an invite

Invites work with or without Google sign-in. On a member, pen invite --auto prints a token that works once within 10 minutes. On the new machine:

curl -fsSL https://pen-relay.pos090001.workers.dev/install.sh | sh -s -- --join <token>

pen invite without --auto also prints the line for a new Windows machine, to run in PowerShell. The token is a secret until it is used: anyone holding it can join in its place.

Use your machines from GOAT

Run pen ssh-config --install on the machine where GOAT runs. It adds an SSH host pen-<name> for every member, with the member’s login user and host keys, and keeps the list current as machines join or leave. GOAT finds these hosts like any other SSH host, so you can open projects and start work on a member by choosing pen-<name>. pen ssh-config --uninstall removes them.

Pen’s hosts set no key to log in with, and a pen-<name> host does not take the IdentityFile of another host you set up for the same machine. If you log in to a member with a key that is not one of ssh’s defaults, add a block for its Pen host to ~/.ssh/config:

Host pen-desktop
    IdentityFile ~/.ssh/id_ed25519_desktop

If ssh pen-<name> says no host key is known for it, that member has published none: pen ls lists such members, and pen ls on the member itself says which key files it could not read and how to fix it.

An SSH connection stays open for 10 minutes after you close it, so the next ssh pen-<name> starts almost at once. ssh -o ControlPath=none pen-<name> opens a separate connection. Windows’s ssh cannot keep a connection open this way, so from Windows every ssh pen-<name> connects anew.

To reach a Windows member over SSH, turn on OpenSSH Server there (Settings, System, Optional features). Pen then publishes its host keys and your login name. When your Windows account is an administrator, OpenSSH reads the keys allowed to log in from C:\ProgramData\ssh\administrators_authorized_keys, not from .ssh\authorized_keys in your profile. For a domain or work account, Pen publishes no login name: use ssh <user>@pen-<name>. Without OpenSSH Server, pen forward still reaches the machine’s other ports.

Some Windows installs let only administrators read OpenSSH’s public host keys, so Pen cannot publish them. Pen does not ask the SSH server for them instead, since another account on the machine could answer in its place. pen ls on that machine says so; to fix it, run this in an administrator PowerShell, then pen down and pen up:

icacls 'C:\ProgramData\ssh\ssh_host_*_key.pub' /grant '*S-1-5-11:(R)'

This lets signed-in accounts read the public keys, which the SSH server shows every client anyway; the private keys stay as they were.

To reach another port, pen forward 8080 <member>:8080 listens on this machine’s port 8080 and connects each connection to port 8080 on the member.

Dashboard

pen dashboard opens a page in your browser, served by Pen on this machine, that shows the mesh: members with their status and how each joined, relays and their health, pending approvals, and recent changes. You can approve or deny requests, remove members, lock the mesh, change relays and create invites from it. It is in Korean and English.

The link works once and only on this machine. Run pen dashboard again for a new one, for example after Pen restarts. pen dashboard --stop closes the page and signs out every open tab.

Remove a machine

Command Use it when
pen leave You are retiring this machine. It leaves the mesh and deletes its keys.
pen revoke <member> A machine should no longer be a member. Every member refuses it from then on.
pen revoke <member> --compromised A machine was lost or stolen, even if it already left. Also removes every machine it admitted, and its unlocks and account changes stop counting. It prints which machine it revokes; when a machine that left and a current one share the name, it stops and prints a command naming each by its fingerprint. A name, a node id (or its first 4 or more characters) and a fingerprint (or its first 8 or more digits) all work, as long as only one machine matches.

A removed machine that is still running shows it in pen ls: “this machine is not a member of mesh …”. To use it again, run pen down there, delete the state folder pen ls names (usually ~/.pen), and join again with an invite or pen login. A member that has not heard of the removal yet still lists the machine until it syncs with one that has; pen revoke <name> on that member removes it there at once.

After --compromised on a mesh with Google sign-in, Pen tells you what else to do: turn on pen lock on, change your Google password, and clear your account’s machine list from the reset link on the sign-in page. A reset ends every sign-in for the account that started before it, so after it only a new Google sign-in registers a machine.

When a member cannot keep a change another machine sends it, the command that made the change (pen revoke, pen lock, pen approve and the like) lists that member as “not taken”, and pen ls on that member says why:

  • “the relay is busy (4429)”: the relay refused the connection for a moment. Nothing is wrong with the member; the change reaches it at the next sync (within 10 minutes).
  • “it cannot write its state folder (4507)”: the member’s state folder is full or not writable. Free disk space or fix the folder’s permissions; the member retries on its own every minute and at each sync, and takes no change until it can save.
  • “its mesh is full (4508)”: the mesh holds 3840 records, the most Pen keeps for new members, names, locks and sign-in changes (removals still fit up to 4096). This happens only in meshes founded before the current Pen; start over in a new mesh, below. A mesh founded by the current Pen gives each group of machines (the founder, and each machine the founder invites with the machines it admits; up to 15 groups) its own room, so one machine cannot fill it for the others, and any machine outside that group can still remove it.
  • “it runs an older Pen than this mesh needs (4509)”: the member holds records of this mesh but runs a Pen from before meshes shared their room out. Update Pen on that machine; machines of a mesh founded by the current Pen all need the current Pen, and an older one cannot join it.

Start over in a new mesh

Use this when a mesh is full, or to split from a mesh you no longer trust. Each machine keeps its keys and name; only its mesh is dropped, and that step needs no other machine, so it works on a machine that cannot reach any member.

  1. On every machine: pen down, then delete these files from the state folder (~/.pen, or PEN_HOME): mesh.json, offers.json, pending.json, forgets.json, versions.json, joined.json and login.json. (pen up on a machine that still has mesh.json starts its old mesh again; it does not found a new one.)
  2. On the first machine: pen up. It founds a new mesh with this machine as its only member. Update Pen on every machine first: a new mesh needs the current Pen on all of them.
  3. On each other machine: pen join <token> with a token from pen invite on a machine already in the new mesh. Joining replaces the machine’s relay list with the inviting machine’s. A machine that used other relays on purpose puts them back with pen relay add <url> (and pen relay rm <url> for one it does not want); pen relay ls then lists them with their uplink state.
  4. If the old mesh used Google sign-in: the new mesh is not bound to the account, and the account is still registered with the old mesh. Reset the account’s machine list at the reset link on the sign-in page, then run pen login on one machine of the new mesh and answer yes to binding it; after that, new machines join it with pen login.

pen-<name> SSH hosts keep working: each machine rewrites ~/.ssh/pen/known_hosts from the new mesh when it starts, and the names stay the same. Machines you did not move stay in the old mesh, which keeps listing the moved ones as members; they are not reachable from the new one.

Relays

Each machine keeps a connection to every relay in its list and uses whichever answers first, so one relay going down does not cut the mesh. An install gets the relays the release lists, and invites carry the inviting machine’s list: pen join replaces the joining machine’s list with it, whether Pen is running or not. pen up --relay <url> replaces the list, also on a running machine. pen login --relay <url> saves that list for this machine before the sign-in starts, and Pen uses it afterwards whether it was running or not, with one exception: a machine where Pen runs in a mesh of its own and that joins the account’s mesh keeps the relays it was using and saves them back. If the sign-in does not finish, the saved list takes effect the next time Pen starts or pen up runs. In every case, check pen relay ls after signing in and use pen relay add or pen relay rm to match the mesh, so the other machines can reach this one. pen relay ls shows the list; pen relay add <url> and pen relay rm <url> change it. Relays must use https.

A relay run with pen relay serve keeps at most 16 MiB of undelivered data for each internet address, so machines behind one home or office connection share it: about four sessions whose receiving side has stopped reading fill it, and until those read again or are cut off (after 10 seconds without progress), new data for that connection’s other sessions is refused. A relay that cannot hold a message ends only the session that sent it, with code 4408; it never drops other sessions or a machine’s own relay connection to make room. Open the session again, and Pen picks a relay again; the machine stays reachable through its other relays.

Two other causes of 4408 on such a relay: all sessions to one machine share a 4 MiB window, so while that machine reads slowly (a busy or slow connection) and one session fills it, data on its other sessions is refused; and a flood from many addresses can fill the whole relay for everyone for a while. In both cases open the session again later; the machine’s other relays are not affected. A new connection refused with 4429 means the machine is taking too many new sessions at once through that relay; retry, or it goes through another relay.

You can run your own relay with pen relay serve on a machine with a public address; see pen help.

Running Pen in the background

pen login, pen join and pen up install a user service (systemd on Linux, launchd on macOS) where they can, so Pen comes back after a restart. With --no-service, Pen runs in the background until the machine restarts; run pen up again afterwards. pen down stops it. On Linux without a systemd user manager (many containers, or su without a login session), pen up says that nothing will start Pen again and prints the command to run at startup. Run it as the same user, with that user’s home, for example from that user’s crontab -e; a startup script that runs as root would start a different machine from root’s home. With systemd but lingering off, pen up prints the sudo loginctl enable-linger line: without it, systemd stops Pen when your last session on the machine ends. Pen writes its log to ~/.pen/daemon.log (on Linux with a service, to the user journal) and keeps it under 4 MiB, with the previous part in daemon.log.1.

On Windows the service is a task in Task Scheduler that starts Pen when you sign in to Windows; it needs no administrator rights. Pen does not run before you sign in: after a restart it starts at your sign-in. pen down stops it until you run pen up again (it does not start at sign-in in between), pen leave removes the task, and if Pen stops unexpectedly it starts again within seconds. Its state is in %USERPROFILE%\.pen, which only your account can read. A --no-service Pen started from an SSH session can end when that session closes.

Cloud boxes and images

Install and join each box on its first boot with --login --yes or --join. Never copy ~/.pen into an image or template: every box made from it would share one identity, and they would keep pushing each other off the relays.

On a box that already belongs to a mesh, run sudo loginctl enable-linger $USER so Pen’s user service keeps running without a login. If your platform runs a startup script when a box starts or wakes (on boxes.dev, the project’s startup script), this one brings Pen back and never starts a new mesh:

#!/bin/sh
[ -f "$HOME/.pen/mesh.json" ] && [ -x "$HOME/.local/bin/pen" ] || exit 0
export XDG_RUNTIME_DIR="${XDG_RUNTIME_DIR:-/run/user/$(id -u)}"
systemctl --user start pen || "$HOME/.local/bin/pen" up

Do not take a template snapshot of a box after it joined. Platforms such as boxes.dev copy the whole machine, including /etc/machine-id, so a box made from that snapshot starts as the same Pen machine and the two push each other off the relays. If that happens, on the copy run pen down, delete ~/.pen and join again; pen leave there would remove the original machine too, since both hold the same keys.

Not supported

  • Direct connections between machines: all traffic goes through a relay.
  • Running Pen on Windows before anyone signs in: it runs as the signed-in user.
  • Managing Pen from GOAT’s settings; use the pen command or its dashboard.
  • Signing in with a Google account the Pen sign-in service does not allow yet. While the service is in testing, only listed accounts can sign in; invites work for everyone.
