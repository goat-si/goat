## Coordinator ruling, verbatim

Coordinator ruling, U56 #796 pairing token scope. Your finding is correct, and #796 does not take on the larger guarantee.
1) Scope: #796 stays the upstream change: when the pairing token is stripped, keep the existing window.history.state (router __TSR_index and user state), remove the token from the URL with replaceState so the history entry no longer holds it, change nothing when there is no token, never navigate back outside the app, and keep the existing auth flow plus hash and query token compatibility. Commit the current red→green helper and history tests for that.
2) Not required in #796: removing the token before the initial document request, before favicon or manifest loads, or before fetchSessionState. The first HTTP request already carries the token to the same server that issued it. Same-origin subresource and fetch requests only send it back to that server, and the default referrer policy (strict-origin-when-cross-origin) sends only the origin across origins. So do not add a no-referrer meta tag, an early in-memory handoff, or any change to query-token compatibility in this row.
3) Verify with path:line in U56.md: no app code makes a cross-origin request carrying the full URL before the strip, and the page sets no referrer policy that would loosen the default. If either check fails, report it to me as a finding rather than expanding the row.
4) Record as a follow-up, not a U56 row: query tokens appear in the initial request line, so check whether the server or any proxy logs request query strings, and consider fragment-only tokens in a separate C4 decision.
Record this ruling verbatim in U56.md.
