# U01 — Desktop boot, readiness and updates

## C4 compatibility (written before implementation)

- #31 — New desktop waits for startup readiness and retains HTTP readiness on the environment descriptor route for older backends. Older desktop can continue using HTTP with the new backend. Provider probes begin after boot. Readiness errors must remain retryable. No state migration.
- #179 — Launcher preflight is local to the runtime. Both generations of client still use the same service protocol. Low space or inaccessible filesystems must not replace a working runtime, skip rollback, or restart-loop. Existing backup/restore format and durable launch intent remain readable on rollback.
- #182 — New client requests stage-only server updates only when the server advertises it, otherwise completes provider installs before using the old update path. Older clients retain the existing install flow. Unauthorized, unsupported, or failed staging may not restart the service. Preserve durable staging and rollback semantics.
- #351 — New server consumes an optionally reported original install token, with the old request-ID default. Older server and old desktop can continue the normal first prepare/install path. Match the artifact and a live prepared lease before returning an original token. Expired or mismatched artifacts and failed downloads follow the existing failure path. No new durable state or lease extension.
- #499 — IPC continues publishing the existing status enum for older renderers, and new renderers accept an older updater's checking state. Keep same-version offers and real errors. Serialize refresh and download admission, and prevent a failed download from becoming installable. No stored state changes.
- #510 — Resume is gated by Cursor SDK and available checkpoint/run data. Existing Cursor sessions remain readable. No native resume without the appropriate checkpoint, and dropped prompts must replay only on the matching local run. Preserve GOAT credential selection, attribution, shell policy and cloud behavior. Reverting restores the previous SDK and patch without changing GOAT DB schema.
- #529 — Application menu shares the update service and its policy/admission gates. Older/newer renderer combinations use existing actions. Available/downloading/downloaded are distinct and a blocked action cannot bypass policy. No persisted menu state.
- #713 — Add the policy distinction as an optional field so older updater payloads still decode and older renderers ignore it. A blocked Nightly must allow an eligible Stable switch while the policy continues to forbid the blocked channel. Existing persisted channel choice and rollback semantics apply.
