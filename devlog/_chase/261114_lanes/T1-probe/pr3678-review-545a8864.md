**P1. A person's terminal request during a restore still deadlocks, now through the per-thread terminal lock**

- **Where:** the restore takes the folder lease, then its setup takes the thread's terminal lock. That happens in `restoreThreadWorkspace.ts:129-142` and `ThreadWorkspaceService.ts:232-244` → `terminal/Manager.ts:2499-2503` (`open` = `withThreadLock`, then `openLocked` `:2494` → `withTerminalLease`). The completion's `closeIdle` (`:3080-3129`) and the forked prompt writer's `write` (`:2890`) take the thread lock too. A person's request goes the other way: the thread lock first, then a wait on the lease. That is true of `open` (`:2499`), `restart` (`:3045-3056`) and attach (`streamSession` `:2673` → `openOrAttachForStream` `:2534`/`:2547`, inside `Effect.uninterruptible`). `KeyedLock` is not reentrant (`packages/shared/src/KeyedLock.ts:16`).
- **Trigger:** while a turn start restore, Restore, Run setup now or Start in a new worktree holds the folder, someone opens a new terminal, restarts one, or attaches to one that has to be started, in the same thread. The window lasts from lease admission until the setup's `closeIdle`, which includes the whole setup script (minutes for a dependency install). For Start in a new worktree, the person's folder is the old one, which `startFresh` also holds (`:170`).
- **Consequence:** a permanent deadlock with no timeout, the same harm as #3674.
  - The restore keeps the folder lease, so turn starts stay Busy and Storage Cleanup skips the folder.
  - The person's request keeps the thread's terminal lock, so every terminal operation on that thread waits.
  - The marker stays set.
  - An attach waits uninterruptibly, so disconnecting the client doesn't free it.
