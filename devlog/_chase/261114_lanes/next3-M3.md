## 7. Decisions for the coordinator (one paragraph each)

**D1, the context chips (notes (i), (xx)) and the other differences between web's and mobile's unsent-answer rules.** When an unsent answer returns to the thread draft, web moves only the context chips the answer text references (apps/web/src/questionAttachments.ts:158, threadContextsReferencedByAnswer from pendingUserInput.ts:83), while mobile merges the question draft's whole context (apps/mobile/src/state/unsent-question-answers.ts:66-70). Read side by side, the other cases agree (whitespace-only answers are skipped by both through appendAnswerToDraft; an attachment with no text moves on both; an equal-text answer is appended on both). One more difference appears once mobile calls the shared parser: mobile's /side also accepts /btw (apps/mobile/src/features/threads/sideChatCommand.ts:2, offered in the menu at use-composer-command-menu.ts:150), the shared parseSideChatCommand does not (unsentQuestionAnswers.ts:8), and upstream's client-runtime has no btw in its parser either (git grep on upstream/main finds btw only in composerDispatch.test.ts:66). My recommendation: (a) mobile follows web on chips, since the owner's O2 decision C reads 'answer text, references and attachments', and a chip the answer never mentioned is context the person did not send; (b) keep /btw on mobile by leaving mobile's composer on its own parser and using the shared one only for answers (question card and inbox), so web behaviour does not change and no web test does; the alternative is adding btw to the shared parser, which changes web.

**D2, 35bda28117 with 7fb54eb051: PORT BOTH.** 35bda28117 is the reason they were deferred (a native Kotlin module needs a native build); this lane rebuilds the dev client anyway for O27 and O24, so the module rides on the same rebuild. Cost: about 300 lines, one Kotlin file, and the fallback path for binaries without the module. Skipping both leaves the Android autofill offer in place. One limit: the emulator has no password manager signed in by default, so 'no login offered' may stay NOT RUN unless I sign the emulator into a throwaway Google account (I will not without your word).
