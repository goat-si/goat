## When updates happen and what the user sees

Codex and Antigravity: GOAT looks for a newer release at most hourly, and only while a client watches the provider's setup with provider update checks on (Settings → Maintenance; gated in providerInstallation.ts). Install or reinstall also checks. Settings → Providers then shows the new version and "Update Codex" or "Update Antigravity"; nothing installs until the user presses it. A fresh install gets the newest verified release (Antigravity) or the pinned one (Codex, and Antigravity when Google's channel is unreachable); an installed release is never downgraded. docs/user/install.md and providers-antigravity.md say this.

## Known limits

- A parent can force stop only its own task children, local or (on a host with taskForceStop) remote (goat#2338); launched threads and other threads still need a person's Force stop. The host cannot tell a remote task binding from a launched-thread binding: the read key authorizes its holder, and the origin restricts force to tasks.
- The child's lane slot stays held until that run ends (PermissionProfiles.unresponsiveStop.test.ts pins the release on completed, interrupted and failed).
- task_cancel drops the parent's completion wake for local children on every provider; that is its contract on dev (OrchestratorMcpService.ts cancel-task-completion-delivery, tested by "returns cancel requested when post-stop disposal fails"), not new with b5b470542a. Its description says to read the child with task_status after a cancel.
- The installer validates new installs with the environment it was built with (unchanged from the integration tip); checks and launches pass the current one.
- 8b21cbdf1e, goat#3374: memory revalidation in the context restore can take up to 10 s, and a user message sent in that window starts its turn first and runs without the restored context.
- goat#3444 (predates this lane): a queued Codex turn that starts after Stop settled it locally (CodexQueuedTurnStop.ts:104-118, CodexAdapterV2.ts:4307) can keep running under an interrupted GOAT run with no Force stop offered when Codex accepts the interrupt and never ends the turn; only the next run's start guard or an unload catches it.
- Codex releases past the pin: the SHA-256 list and the archive come from the same GitHub release, so the digest catches corruption, not a compromised release; redirects are followed and there is no host allow-list; the offered range is the open-ended ">=0.156.0".
- Antigravity releases past the pin: the SHA-512 comes from the hard-coded Cloud Run manifest host (antigravity-cli-auto-updater-974169037036.us-central1.run.app) and the archive from the storage.googleapis.com/antigravity-public/antigravity-cli/ prefix; tampering with the bucket alone is caught, while control of the manifest service can pick only a published release for the platform that the model manifest marks supported (>=1.5.1 <2 in the bundled manifest).
- goat#2338: once a child is forced, only a person can force stop that child's own unresponsive children. On macOS (agentMemoryGuard.ts:344) and Windows (agentScope.ts:107) killing the thread's agent process group does nothing, so force only releases the session and the outcome is never killed. A detached shared session leaves the stuck turn running out of sight. Local force acts on the child thread's live run, including a later continueFrom round; remote force acts only on the task's launched run. Remote force needs a full-access, default-mode parent with an active run (RemoteTaskTargets.ts:91-104); local force does not.
- goat#2338, macOS and Windows: the re-check and the (no-op) kill run under the thread lock, but the settle and the session teardown run after it. A provider that confirms Stop in that gap leaves its idle session released and the parent told the run was ended by force. On Linux the kill happens under the lock after the re-check, so the window is closed there.
- Musl Linux: when Google's channel is reachable but offers only a release the model manifest does not mark supported, Install still says "No Antigravity release is available to install. Check the network connection and try again."; the network hint is wrong in that case.
- Both: the supported/withdrawn decision comes from upstream's manifest on raw.githubusercontent.com/pingdotgg/t3code/main. No code signature or notarization is checked. The downloaded binary runs during install, before any session: codex --version with the server's environment, and agy acp initialize.
