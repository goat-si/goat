## C4 answers

### A. Network

Verdict: with GOAT's configuration nothing leaves the device. Evidence is from the published tarballs (integrity-checked against the lockfile; unpacked under /tmp/goat-chase-261114/mobile-i18n/tar/) plus the L14a audit of the shared GT runtime packages (/tmp/goat-chase-261114/i18n-research.md).

- **Catalogs are bundled and loaded locally.** `I18nProvider.tsx` imports the eight catalogs statically and passes `loadTranslations: async (locale) => TRANSLATIONS[locale] ?? {}` to `initializeGT` with no projectId, apiKey, devApiKey, cacheUrl or runtimeUrl. `initializeGT` is react-core's `internalInitializeGTSRA` (gt-react-native src/setup/initializeGT.ts:8). With `loadTranslations` set, gt-i18n picks the `custom` loader ahead of any CDN option (gt-i18n 1.0.40 dist/versionId-BDwkPmu8.mjs:129-134; routeCreateTranslationLoader `case "custom"`, dist/internal.mjs:494). The only catalog fetch, `createRemoteTranslationLoader` (internal.mjs:448-458), is unreachable.
- **Runtime translation is off.** Its API type needs `projectId` plus a key in the init params (versionId-BDwkPmu8.mjs:142-147), and the dev hot-reload gate needs `devApiKey` and `projectId` in `runtimeConfig`, which is built from the params only (:220-227, :271-273). Mobile uses only `useGT` (no `<Tx>`), whose miss paths are gated as the L14a audit records.
- **Env vars.** No environment variable switches remote translation on for the app. gt-react-native has no `process.env` or `EXPO_PUBLIC_` reads at all; react-core reads only `NODE_ENV`; gt-i18n reads `NODE_ENV` and `_GENERALTRANSLATION_LOG_LEVEL` (logging). The one credential read is generaltranslation 9.5.9's `GTRuntime` constructor, `process.env?.GT_API_KEY`, `GT_DEV_API_KEY`, `GT_PROJECT_ID` (dist/runtime.mjs:40-44). Those cannot reach the app: babel-preset-expo inlines only `EXPO_PUBLIC_*` and `NODE_ENV` (apps/mobile/babel.config.js has no other env plugin), and the instance only feeds `translateMany`, which sits behind the params-only gates above. For the CLI, which this lane does not ship in apps/mobile, `GT_PROJECT_ID`, `EXPO_PUBLIC_GT_PROJECT_ID` and nine other `*_GT_PROJECT_ID` names plus `GT_API_KEY` would enable `gt translate` (gt 2.27.0 dist/fs/utils.js:2-15). No `.env` exists in apps/mobile or the repository root (only `.env.example`).
- **Native module.** iOS `GtReactNative.mm` reads `NSLocale` and reads/writes `NSUserDefaults` (:22-53); Android `GtReactNativeModuleImpl.kt` reads `LocaleList` and the private `gt_store` SharedPreferences (:18-55); the Android manifest declares no permission. GT persists the resolved locale there under `generaltranslation.locale` (gt-i18n dist/internal-cookies.mjs:4), on the device only.
- **No call-home code.** Across gt-react-native and the 12 FormatJS packages, excluding maps and docs, there is no `fetch(`, `XMLHttpRequest`, `WebSocket` or `sendBeacon`; gt-react-native's only URLs are package metadata and one FormatJS issue link in a comment of its unused Babel plugin (src/plugin-dir/types.ts).
- **Hardening.** No `i18n:translate` script (and no `i18n:generate`, item 5). `cacheUrl: null`/`runtimeUrl: null` are not added: both paths are already closed by the custom loader and by params-only gates, and the web lane did not add them either.

### C. Contracts and settings

- The mobile `language` value is a device-local preference in `MobilePreferences` (SQLite, secure-storage fallback). It crosses no wire and is no server setting, so `SETTINGS_ACCESS` does not apply: `SettingsKey` is `keyof ServerSettingsPatch.fields` (packages/contracts/src/agentSurface/settingsAccess.ts:14). No contracts change. It is separate from web's client setting `language`; nothing syncs them, as upstream.
- Older peers are older or newer builds of the app on the same device. Preferences saved before this build have no `language` and load as unset, which renders English. An older build drops the key on its next save (its sanitizer copies only known keys), so a later upgrade reads English again. A locale this build does not ship (from a newer build) is kept and resolved like System default. A non-string value is dropped.
- Tests: `apps/mobile/src/persistence/mobile-preferences.test.ts` (the real store on its fallback path): the chosen language survives a restart; a non-string language is dropped (negative); preferences from a build without the setting load with it unset (older peer). `packages/client-runtime/src/locales.test.ts`: unknown locales resolve like System default, Traditional Chinese hosts stay off `zh`, and a client only matches locales it ships.
